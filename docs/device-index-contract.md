# 设备标识与索引契约（平台侧对齐说明）

> 本文面向 **北向平台 / 上位机对接方**，说明本次修复后 `channel_index` / `device_index` /
> `device_code` 的语义与变更点。网关侧已按本文实现；平台侧需按下文第二节核对。

## 一、问题背景（修复前的缺陷）

修复前，`DevicePlan.Index` 由服务端按「数组追加顺序」重新编号：

```go
dp.Index = len(plan.Devices)   // 忽略配置里已有的 index
```

而会被跳过的设备有四种来源：设备模型被删除、`commNo` 越界、`commNo` 通道内重复、
属性校验失败。任一设备被跳过，后续所有设备的索引都会**整体前移**。

由此产生的后果是数据错位，而不是报错：

| 配置 | 运行期索引 | 后果 |
|---|---|---|
| `[dev0 正常, dev1 模型已删, dev2 正常]` | dev0 → 0，dev2 → **1** | 平台按拓扑查到的 `device_index=2` 下发写命令 → 越界失败 |
| `[dev0 模型已删, dev1 正常]` | dev1 → **0** | 平台的 `device_index=0` 命中 **dev1**，按 index 缓存的历史数据会串 |

更关键的是，`device_index` 直接参与北向唯一编码：

```
device_code = {gw_id}{channel_index:03d}{device_index:03d}
```

所以一次「删除设备模型」的配置操作，就能让 `gw_001001002` 这个编码从「2 号设备」
变成「1 号设备」，历史数据、告警规则、点表映射全部错位，且没有任何错误提示。

## 二、修复后的契约（平台侧按此核对）

### 2.1 索引即稳定业务标识

- `device_index` **等于**通道配置 `devices[].index`，由服务端在创建设备时分配，
  **运行期永不重排**。
- 索引分配规则：取当前通道内最小未占用的非负整数（与 `channel_index` 同规则）。
- 设备配置失效（模型缺失 / 通讯号非法 / 属性校验失败）时：
  - 该索引**保留占位**，不会被后续设备复用；
  - 该设备 `valid=false`，不参与采集；
  - 平台侧对它的写命令会收到明确失败回执，而不会静默命中别的设备。

### 2.2 拓扑查询新增字段

`queryTopology` 响应中的 `channels[].devices[]` 增加 `comm_no`：

```json
{
  "index": 2,
  "name": "1#进线柜",
  "comm_no": 12,
  "datasheet": [ ... ]
}
```

| 字段 | 说明 |
|---|---|
| `index` | 设备序号，稳定，与 `.data` / `.cmd` 消息中的 `device_index` 一致 |
| `comm_no` | Modbus 从站地址。**新增**，供平台侧与现场点表交叉核对 |
| `datasheet` | 属性清单，不变 |

> `comm_no` 是平台侧识别「这台设备到底是哪一个物理从站」的最直接凭据。
> 建议平台在入库时同时保存 `(gw_id, channel_index, device_index)` 与 `comm_no`，
> 后续若发现 `comm_no` 与预期不符，即可判定为配置错位。

### 2.3 无效设备也保留在拓扑中

修复后拓扑**包含**配置里有误的挂载项（保持序号连续可解释）。
若某设备配置有误，它会照常出现在 `devices[]` 中，但不会产生 `.data` 消息。

平台侧处理建议：
- 不要假设 `devices[]` 里每一项都在持续产生数据；
- 超时判定应以「曾经收到过数据、随后停止」为条件，而不是「拓扑里有但从未收到」。

## 三、是否需要平台侧改动

**结论：仅当平台侧曾依赖「索引重排」这一缺陷行为时，才需要改动。** 分三种情况：

### 情况 A：平台按拓扑动态发现设备（推荐做法）

无需改动。拓扑里的 `index` 现在更稳定，原有逻辑只会更可靠。

### 情况 B：平台侧硬编码了 `device_code`

需要核对。因为 `device_code` 的**格式没有变**（仍是 `{gw_id}{ch:03d}{dev:03d}`），
变的是「同一个索引指向哪台物理设备」。核对方法：

1. 取现场网关导出的拓扑快照；
2. 对每个 `device_code`，比对 `comm_no` 与现场点表是否一致；
3. 不一致的，说明该设备此前曾被重排过，历史数据需要按新的 `comm_no` 归属修正。

### 情况 C：平台用 `device_index` 作为主键持久化历史数据

建议迁移到 `device_code`（含 `gw_id`，天然跨网关唯一），或在原主键上补存 `comm_no`。
`device_index` 只在单网关单通道内唯一，作为跨网关主键本身是有风险的。

## 四、`device_code` 的边界情况

索引为 0~999 时保持定宽拼接：

```
gw_001 + 001 + 003  →  gw_001001003
```

索引溢出 999 时，定宽拼接会产生**长度变化**导致平台解析串位。修复后的行为是：
**改用分隔符形式**，让错位变成可见的格式差异：

```
gw_001:1001:3
```

若平台侧有 1000 台以上设备的通道，请优先支持分隔符形式。
正常场景（<1000 设备/通道、<1000 通道）行为与之前完全一致。

## 五、其他相关契约变更

| 项 | 变化 | 影响 |
|---|---|---|
| `.cmd` 回执 | 队列满时 `message` 改为「写命令队列已满或链路未就绪」 | 文案变化，`status` 枚举不变 |
| 离线心跳 | 由「每 500ms 全设备离线报文」改为「状态翻转发一次 + 30s 心跳」 | **下行流量显著下降**，平台侧不应依赖离线报文的高频特征做存活判定 |
| 异常码 | 从站返回异常码时不再盲目重发（Busy/Acknowledge 除外），并立即上报真实原因 | 平台会更快收到「非法数据地址」这类确定性错误，而不是统一的「超时」 |
| 写命令 | 支持 `writeFunctionCode=16`（单帧多寄存器）与 `=6`（逐寄存器拆帧）两种策略 | 见下节 |

## 六、写功能码 06 / 16 的选择（含平台侧关注点）

当一个属性横跨多个寄存器（32 位 float、32/64 位整数）时：

| 模型配置 | 网关行为 | 适用场景 |
|---|---|---|
| `writeFunctionCode = 16` | 用 **一帧 FC16** 写完全部寄存器 | 规范做法，绝大多数设备支持 |
| `writeFunctionCode = 6` | 按寄存器**逐帧 FC06** 写（地址升序） | 设备不支持 FC16，或写连续寄存器会触发整体块校验 |

要点：

- 平台侧看到的是一次写命令 → 一次回执，拆帧对平台透明；
- 但拆帧是**非原子**的：若第 2 帧失败，第 1 帧已生效，网关会回执失败并说明已应用的帧数；
- 因此**优先配置 16**。只有确认设备不支持时才用 6，并接受非原子风险。

## 七、网关侧验收清单

平台侧可要求网关提供以下证据：

- [ ] `GET /api/engine/status` 中每条链路的 `devices[].index` 与配置 `devices[].index` 完全一致；
- [ ] 手动删除一个正在被挂载的设备模型后，其余设备的 `index` 不变；
- [ ] 该被删模型对应的设备在 `devices[]` 中 `valid=false` 且 `error` 字段说明原因；
- [ ] 对该设备下发写命令，收到 `status=failure` 回执，且**没有任何其它设备收到写入**；
- [ ] `queryTopology` 响应中每台设备都带正确的 `comm_no`。
